## 1. The mission — the "why" (the founder's north star, in their words)

> "These lessons are supposed to help our users L3ARN faster, more efficiently, more sticky and more fun. If the lessons don't teach according to the child's learning style as well as the parent's learning preferences, as well as the standard level of competency for the subject, we have failed miserably. The MAIN focus of this app is to give children a leg up in education not only by making it engaging and interacting but also EFFECTIVE. We are positioning our children to L3ARN with AI. To L3ARN and apply AI to our education. To L3ARN and master the core skills that supersede the standard benchmarks locally, state wide, nationwide and then WORLDWIDE."

**Non-negotiables that fall out of this:**
1. **Effectiveness is the point**, not engagement alone. A fun clickthrough that teaches nothing is a failure.
2. A lesson MUST adapt to three inputs simultaneously (this is already the app's stated "three-part constraint," ADR-014):
   - **Child's learning style** (how this specific child learns best)
   - **Parent's learning preferences** (parent-set curriculum focus, approach, boundaries)
   - **Standard competency level for the subject** (grade/standards baseline — and the goal is to EXCEED it)
3. Kids **learn WITH and APPLY AI** — the "catch the AI's mistake" beat is core to the product thesis (AI literacy), not decoration.
4. Master core skills that **exceed** local → state → national → world benchmarks.

Also load the app's guiding principle (project memory / Master Protocol):
**"Parent config = starting hypothesis; student behavior = ground truth."** The lesson engine must start from parent/standards config and then adapt from what the child actually does.

## 2. The current state — the brutal technical truth (so you don't re-discover it)

I (previous agent) read the deployed lesson code end-to-end. **Do not re-explore before understanding this section — it is accurate as of `origin/main` on 2026-07-05.**

### 2a. The AI writes the STORY, not the LESSON

Two separate systems, and only one is intelligent:

- **AI-generated (personalized):** ONLY the **briefing screen** — `storyHook`, a task-preview list, `rewardPreviewLabel`. Generated by `packages/mission-compiler` `compileStart()` (fast path, ~5s, `contentSource:"ai"`, model `claude-haiku-4-5`). Personalized to the child's house + companion.
- **The actual gameplay** is **6 HARDCODED React steps** in `apps/web/src/app/(student)/mission/[missionId]/MissionExperience.tsx` (~1056 lines). These steps **completely ignore the AI mission**. Every child on earth gets the identical six steps, identical words, identical "correct" answers.

### 2b. The steps barely qualify as a lesson

| Step | Component | Reality |
|---|---|---|
| 0–2 | `CrystalSortStep` | **A single button** (`"Blue Bin — click to sort"`). No second bin, no wrong answer possible, no discrimination. The companion asks "what do these crystals have in common?" but the UI gives nothing to answer with. You click one button → "sorted!" → next. **The child cannot be wrong**, so it cannot teach. `tryCapture(..., "sequence-completion")`. |
| 3 | `AIMistakeStep` | 4 **hardcoded** options (`AI_MISTAKE_OPTIONS`), hardcoded correct answer. The AI-literacy beat — good concept, static execution. |
| 4 | `ExplainRuleStep` | 4 **hardcoded** options (`EXPLAIN_OPTIONS`), hardcoded correct. |
| 5 | `ReflectionStep` | Hardcoded `REFLECTION_OPTIONS`, no right/wrong. |

Companion dialogue = **static `useState` string literals**, swapped to other hardcoded strings on click. Not AI. Not adaptive. Not a tutor.

### 2c. Every gap the founder named is real and currently absent

- **No real teaching** — no-fail buttons build no concept, give no "why," create no productive struggle.
- **No adaptation** — interactions are fixed English text. Grade level and reading level change NOTHING in the actual lesson. A child who can't read the sentence has no path.
- **Companion is not a helper** — static caption. No adaptive hints, no "explain it differently," no read-aloud/audio, no alternate representation, no scaffolding tuned to THIS child's wrong answer.
- **No exit during gameplay** — `handleExit()` exists but is NOT rendered while `phase === "step"`. The child is trapped until completion. (Rendered only on error/done/briefing/dev-fallback screens.)

### 2d. What DOES exist and works (build on it, don't rebuild)

- **Mission Compiler** (`packages/mission-compiler`): `compile()` generates all six mission output types; `compileStart()` generates only `student3dMission`. There is a **richer schema already defined but only partially used** — `validation/mission-output.schema.ts` has `AIRawMissionOutputSchema` (parentPlan, student3dMission, interactiveLite, textAudioOffline, evidencePlan, rewardPlan). `MissionTask.interactionType` enum is already `click | drag | choice | text-input | observe | sequence` — richer than the UI actually uses.
- **Evidence + mastery pipeline** (WORKS, but is fed by fake interactions today): `tryCapture()` → `learning_evidence_events`; `mission/complete` → `mastery_records` (with evidence proof-chain), rewards (moolah/xp/house points/badges/companion bond), `parent_reports` (First Learning Map). Confirmed live: completion writes all of this.
- **Learner calibration** from House Calling ceremony → `academy_identities`, `house_calling_signals`, calibration signals (a learning-style signal source already exists).
- **Parent curriculum prefs**: `parent_curriculum_prefs` (focus_subjects, approval_mode) — JUST fixed this session (PR #34) so it persists and is readable.
- **Curriculum spine / standards**: `mastery_domains`, `mastery_skills` tables (service-role), `floridaStandardCode` field in schema — the standards-alignment substrate exists.
- **Companion system**: `companion_profiles` (bond level, character), companion selection flow.

### 2e. The three-part constraint is declared but under-delivered

`MissionCompilerInput` already carries `parentIntent`, `childPersonalization`, `masteryTargets` (ADR-014). But `compileStart()` uses them only to flavor the STORY; the standards/mastery targeting is thin, the child-learning-style input is minimal, and none of it reaches the actual interactions (which are hardcoded). **The constraint exists as a data shape; it is not yet the engine that drives what the child sees and does.**

## 3. The design questions the session must resolve (your starting agenda)

Explore these **one at a time** (brainstorming discipline). Don't accept vague answers like "make it adaptive" — force concreteness.

1. **Define "effective."** How do we know a lesson taught? (mastery evidence from real discrimination, not click-through). What's the measurable bar per lesson?
2. **Learning-style adaptation — get concrete.** What learning styles/dimensions do we support? Where do they come from (House Calling calibration + parent prefs + observed behavior)? **What literally changes** in a lesson for a visual learner vs. a reader vs. a kinesthetic learner vs. a struggling reader? (Not abstractions — the actual screen difference.)
3. **Reading level / accessibility / non-readers.** Read-aloud (TTS)? Simplified-language tiers by grade + observed ability? Visual-first / audio-first alternatives? What's the path for a child who can't read the prompt at all?
4. **Companion as a live tutor.** Real runtime AI hints that respond to THIS child's specific wrong answer; "explain it a different way"; Socratic prompting; scaffolding that escalates. Where does companion intelligence run (client? Railway? which model?) and at what latency/cost?
5. **Real interactions.** The sort step needs genuine discrimination — multiple bins, wrong answers possible, productive struggle, feedback that explains WHY. Generated per-child and tied to the concept. What interaction primitives do we need (sort/match/sequence/multi-select/free-response-graded/…)?
6. **Standards & "exceed the benchmark."** How does a lesson map to a standard, gate on mastery, and then push beyond grade level for kids who are ready?
7. **Generation vs. authoring — the big architectural fork.** How much is AI-generated at runtime, vs. authored templates the AI fills, vs. a hybrid content pipeline? (This decides everything about reliability, latency, cost, and safety.) The founder explicitly asked to "deep dive into the lesson planning and the mission planning configuration to really understand how to properly configure these lessons." **Lesson authoring/config is in scope.**
8. **Parent's role.** How do parent learning preferences + curriculum focus + approval mode concretely shape a lesson?
9. **Exit / save / resume.** Leave a mission and come back where you left off.
10. **Safety & quality gate on AI-generated pedagogy.** Age-appropriate, factually correct, no hallucinated "correct" answers, no harmful content. A wrong "correct answer" in a lesson is a catastrophic failure. How do we guarantee correctness of generated pedagogy?
11. **Latency / pre-generation.** Real adaptive lessons cost more generation than the ~5s story. Options: pre-generate during onboarding/companion-selection (the child spends 1–3 min there), cache per child+concept, or a stronger model async. (Flagged earlier as a live lever.)

## 8. Scope guidance (decompose — don't boil the ocean)

This is genuinely large (a lesson ENGINE + authoring/config pipeline + runtime adaptive tutor + accessibility + standards mapping). It almost certainly needs decomposition into sequenced sub-projects, each with its own spec→plan→build cycle. A plausible decomposition to propose (let the user steer):

1. **Lesson content model + generation contract** — the schema/contract for an adaptive lesson (interactions, correct-answer provenance, learning-style variants, reading-level tiers, standards mapping, safety gate). The foundation everything else builds on.
2. **Adaptive lesson runtime** — the frontend engine that renders REAL interactions from that contract (replacing the hardcoded steps), with exit/save/resume and accessibility (TTS, language tiers).
3. **Live companion tutor** — runtime adaptive hints/re-explanation/scaffolding driven by the AI, responding to the child's actual actions.
4. **Generation + config pipeline** — how a lesson is authored/generated/validated/cached (the "lesson planning and mission configuration" the founder asked to deep-dive), including the correctness/safety gate and pre-generation timing.
5. **Effectiveness measurement** — evolving the evidence/mastery pipeline to prove real learning and drive the parent→hypothesis / behavior→ground-truth adaptation loop, including exceed-the-benchmark progression.

**Recommend brainstorming (1) first as the keystone**, since the runtime, tutor, and pipeline all depend on the lesson content contract. But confirm the decomposition and starting point WITH the user before diving into any single spec.
